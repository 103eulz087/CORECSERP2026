## Bugs Encountered (known patterns)

- **`.Text` vs `.EditValue` (Known Bug Pattern #3)** — the headline bug of the day. Hit in `AccountingReportsForm.cs`'s branch selector (root cause of the Trial Balance "branch 888 returns 0" report) and, defensively, in its account-code selector. Recurred badly enough (twice, with the second instance introducing a new regression) that the fix pattern itself is worth internalizing: swapping `.Text`→`.EditValue` on an unselected control can turn an "obviously empty/wrong" failure into a "silently reads as the same sentinel used for an intentional NULL/All" failure — always pair the swap with a required-selection guard if there's no upstream guarantee a value is always selected.
- **New pattern worth adding to CLAUDE.md**: a signed running-balance column (`GLSummary.EndingBalance`) used one uniform sign convention across every account regardless of category (`Nature`), but the reporting SP's Debit/Credit column split was gated by that category anyway — mixing "which column does this number belong in" (pure sign) with "is this sign normal for this account" (category-dependent). Worth calling out explicitly next time similar signed/categorized balance logic is touched (Balance Sheet, Income Statement, GL Detail already checked clean for this specific pattern today).
- **LoadData() ordering** — checked, not violated: `ConversionPerBarcode.LoadData()` remains the real init entry point across both features added today; `AddBranchOrderSTSBatchMode`'s column-hide logic in `_Load` was verified to run only after the caller populates the grid (no `LoadData()` on that form, but the same "don't gut init into Load" spirit was respected).
