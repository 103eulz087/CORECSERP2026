H1GL ticket writer can post an unbalanced ticket and hides its errorsTier AIn progress · Fable, DEV + STAGING done, PRODUCTION pending›

Problem

  • sp_PostCompoundTicket (PV-AP payment legs, inventory posting, upload finalize) has no debit = credit check.
  • An amount type the caller didn't supply falls back to GROSS: PV-AP-DISC / PV-AP-EWT-DISC post the discount leg at the gross amount; the PV-AP bank leg uses gross, not net.
  • Every error reaches the screen as 50050 'ERROR SP'.
  • The FX loss mapping points at 60302 (Bad Debts); 60323 is the FX account (accountant to confirm).

Harden

  • Assert balanced per ticket and branch before the insert, with its own error number.
  • Refuse a missing amount type instead of defaulting; re-throw the original error; check every mapped account against the chart of accounts. Keep the signature (incl. @LedgerSide from [71]).

Done when

  • Balanced postings identical old vs new (rolled back, per mnemonic); unbalanced and missing-type cases refused.
  • New Exception Center check "any ticket with DR ≠ CR, all modules" is 0 on DEV, STAGING and PRODUCTION.

PRODUCTION 10-14: no balance check in the definition; still re-throws as 50050.

H2Reversing an AR payment can reverse another customer's sales ticketTier AIn progress · Fable, DEV + STAGING done, PRODUCTION pending›

Problem

  • sp_ReversePaymentClient mirrors every ticket and client-ledger row WHERE ReferenceNumber = @refno.
  • Sales tickets keep the PO number in the same column, from a different counter. When the numbers meet, the reversal also mirrors that sale.

Harden

  • Scope tickets to the payment's own OR-% mnemonics and the ledger to the customer + OR-% trans codes; refuse when the scope is empty or touches a second customer.
  • Review every other reversal that selects by ReferenceNumber alone (Dependency Atlas).

Done when

  • A forced collision on DEV (rolled back) mirrors only the payment; normal reversals produce identical rows to today's.

PRODUCTION 10-14: not scoped. No collision yet (DEV had 34), so it is waiting to happen.

H3Rollbacks and re-throws hide the real error, including the month lockTier AIn progress · Fable, DEV + STAGING done, PRODUCTION pending›

Problem

  • Named rollbacks (ROLLBACK TRANSACTION PaySupplierV2) raise 6401 when nested and hide the cause.
  • sp_AddPaymentSupplierCompound*, sp_AddPaymentClient, SP_CONFIRMPO, sp_ReversePaymentClient, SP_UPLOADINVENTORY turn the month-lock refusal (59900) into "no BEGIN TRANSACTION"; RAISERROR(@msg) becomes 50000.

Harden

  • One standard for every posting proc: XACT_ABORT ON, TRY / TRAN / COMMIT, CATCH: IF XACT_STATE() <> 0 ROLLBACK; THROW;. Safe with or without an outer transaction. Written into docs/standards/.

Done when

  • Success path identical; a forced 59900 surfaces as 59900; no 6401 inside an outer transaction. Prerequisite for H4.

H5Payments settle against the amount on screen, not the current balanceTier AOpen›

Problem

  • Known Bug #10 is fixed only in the telegraphic voucher. Supplier payments (expense and purchase) settle with the screen's amount.
  • sp_AddPaymentClient recomputes Balance = TotalAmount − (AmountPaid + EWT + Discount + Offset); any invoice whose balance was set directly is silently reset by its next payment (fixed once for balance-forward rows by [43]).
  • Credit memo, return and cash advance: not audited yet for this pattern.

Harden

  • Re-read each balance under UPDLOCK; refuse a stale screen with its own code; make balance updates incremental, or assert the formula before applying it.

Done when

  • A two-session test (grid loaded, invoice paid elsewhere, then submit) is refused; the normal path is identical; invoice = ledger checks stay 0 for AP and AR.

PRODUCTION 10-14: the AR balance formula is still a recompute.

H6Lookups can hand back a different record than the one pickedTier AOpen›

Problem

  • SearchLookUpClass.getSingleValue reads the popup's focused row, not the picked one; the first pick after load can return another row.
  • With a non-unique value member (938 customers share a name) a payment or order can post to the wrong party with no error. Fixed only in Client Payments so far.

Harden

  • Fix the helper centrally (EditValue / GetSelectedDataRow()), then audit every lookup for a unique value member (composite keys, Known Bug #7) and DisableTextEditor (Known Bug #2). Posting screens first.

Done when

  • Per converted screen, the first pick after load returns the picked row and a duplicate-name pair resolves to the right key; the user gets the list for a UI pass.

Code 10-14: 131 calls in 55 files.

H7Bank recon loopholesTier BOpen›

Problem

  • sp_Payment_PostBankReconEntry silently does nothing on a second call for the same reference, account and side (Known Bug #9).
  • JV and multi-branch expense edits delete and re-post their recon rows, so a cleared item comes back open.
  • The manual-lines payment updates an outstanding-cheque amount without checking cleared / locked; delete and save of recon items skip the period lock.
  • sp_BankRecon_AutoMatch (clears cheques from their own GL credit, not the bank) is still installed; only its buttons are hidden.

Harden

  • Refuse or report a second call that would change an amount; keep cleared items cleared across edits; lock checks on every recon writer; drop or disable Auto-Match (user's decision).

Working together

Who owns what

  • Fable: hardening, one backlog item at a time.
  • ERP session: user requests, data repairs, deployments, Exception Center checks; verifies each item Fable hands back.
  • The user: picks the next item, approves STAGING, runs PRODUCTION.

Rules for every item

  1. Claim it in the handoff file before touching code; the other session leaves its objects alone.
  2. Read the live definition on DEV and STAGING first; repo copies can be older.
  3. One shared [NN] script series; claim the number in the work log.
  4. Stay compatible with the current exe and the web v2 (optional parameters, opt-in behaviour, _OLD_ backups).
  5. DEV → rolled-back STAGING rehearsal on the user's go → the user runs PRODUCTION; verify read-only.
  6. Add an Exception Center check that proves the rule; record the rule in the work log.
  7. Hand back with a result line; the ERP session marks it verified.
